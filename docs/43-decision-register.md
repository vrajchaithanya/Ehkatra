### Session 3 (2026-08-07) — local build host
**D-035 — Two dependency budgets, both gated.** DP-S2 (docs/07 §3) says "kernel ≤ 5 external crates (currently 1: blake3)". That count was *direct edges*; the actual compiled-in closure is 10, because `blake3` brings 9 (SIMD/build-script support). Rather than silently reinterpret the rule to make it pass, `tools/dep-budget.mjs` gates both: **direct ≤ 5** (DP-S2 as written, at 1) and **closure ≤ 12** (new, at 10). Raising either ceiling requires an ADR. Alternative rejected: enabling blake3's `pure` feature to drop `cc`/`shlex`/`find-msvc-tools` — it removes the SIMD path and so trades a measured hash-throughput loss for a cosmetic dependency count; revisit only if the closure budget is actually pressed.

**D-036 — Exact toolchain pin in `rust-toolchain.toml` (implements D-034).** `channel = "stable"` let clippy drift between sessions and turned a green gate set red on a codebase nobody had touched (two lints: `needless_range_loop`, `explicit_counter_loop`). Now pinned to `1.97.1` with `components = [clippy, rustfmt]` and `targets = [wasm32-wasip1]`, so a fresh clone reproduces the toolchain automatically. CI stopped specifying a toolchain and reads the file. Cost: a deliberate, dated bump each release train — which is what D-034 asked for anyway.

**D-037 — `Cargo.lock` is committed.** It was git-ignored. This workspace ships binaries, and DP-A2/DP-E8 require a commit to rebuild with the same dependency set; an unlocked build is a determinism claim with a hole in it.

**ADR-034 — Tile bands are keyed by stable *slots*, assigned at first observation in canonical order.**
Context: tiles are keyed `(RowBand, ColBand)` "in identity space" (docs/14), but identities are 192-bit `OpId`s with no ordinal. Something must map identity → band.
Decision: intern each row/col identity to a **slot** the first time replay observes it, in canonical `(lamport, actor, counter)` order; `band = slot / 256` (rows) or `/ 64` (cols). A slot never changes for the life of an identity.
Alternatives rejected: **(a) band from live position** — perfect locality, but one row insert re-keys every tile below it, destroying content-addressing and forcing full re-transmission on sync; also a direct DP-A6 violation. **(b) band from `hash(OpId)`** — perfectly stable and ordering-free, but scatters neighbours across tiles, which deletes the entire point of tiling.
Consequence: locality is excellent for the dominant creation-order case (import, append, fill) and degrades gracefully under heavy interleaved insertion. Slot values depend on the op *set*, so a replica holding a subset may assign different slots — this is safe **because no hash, op, or convergence property depends on a slot's value**, only on its determinism for a given set. Proven by `inserting_a_row_never_rekeys_existing_tiles` and `tiled_state_converges_under_reordering`.

**D-039 — Promotion is decided per *contested cell*, in a replay pre-pass; and A-002 fails against it.**
Two sub-decisions, recorded together because the second is the reason the first matters.
*(i) Predicate.* A tile promotes if **any single cell in it was written by two or more actors**. The first implementation used the coarser "two actors wrote anywhere in this tile" and measured **100% promotion on every multi-author pattern** — co-located collaborators are not a conflict, and a 16,384-cell tile makes co-location nearly certain. The per-cell predicate costs one 2 KiB bitmap per (tile, actor) transiently in the pre-pass, and is a large, measured improvement.
*(ii) Timing.* Promotion is decided in a **pre-pass over the ordered ops, before any write lands**, not lazily on conflict. Reason: a summary tile records no per-cell stamps, so if asked to promote later it could not reconstruct them, and any reconstruction (e.g. stamping every cell with the tile's max lamport) would silently change LWW winners — a DP-A8 violation dressed up as an optimisation. The cost is a second pass over the log; `State::replay` sorts anyway, so it is asymptotically free.
*Outcome, recorded honestly:* even with (i), **A-002 fails** — 0.1% contested cells promote 25–100% of cells, and the memory cost (74.5 B/cell) puts a 10M-cell workbook at ~745 MB against a 400 MB budget. ADR-005's tile granularity is the thing under question, not the predicate. Redesign options to weigh at the Q1 gate: sub-tile promotion blocks (e.g. 64-cell groups), per-cell promotion with a compact stamp (delta-encoded lamport + actor index), or a two-level summary. Do not pick one without re-running `tools/tile-bench`.

**D-040 — The state hash now folds cells in tile-major order.** Superseded value: `4516044e…` → `e6cc2757…` for the replay-check corpus. docs/10 specifies "BLAKE3 Merkle tree over tiles", so tile-major is the documented direction and it is O(n) with no extra allocation; flat identity order would have needed either an O(rows×cols) scan or an O(cells) sort buffer. Identities, never slot numbers, are what get hashed, so DP-A6 is intact. The **oplog** hash is unchanged (`77e5b1bf…`), which is the evidence that the op algebra itself did not move — DP-A4's immutability is about op semantics, and the state hash is explicitly a determinism-gate primitive, not a wire format.

### Session 4 (2026-08-07) — Row 5, the value lattice

**ADR-035 — `Decimal` is a 128-bit scaled integer, and is deliberately *not* IEEE 754-2008 decimal128.**
Context: ADR-010 says "Decimal128 alongside f64". Implemented literally, that means densely-packed-decimal encoding, ±Infinity, NaN/sNaN, five rounding modes, and cohort/quantum preservation — thousands of lines plus a conformance suite, in a `no_std` kernel with a 5-crate budget.
Decision: `{ coefficient: i128, exponent: i16 }`, canonically normalised (trailing zeros stripped). **38 significant digits, four more than real decimal128**, with exact `+ − ×`, exact comparison, and half-even division; all integer arithmetic, no float path, no panics — overflow returns `None` and the value layer raises `#NUM!`.
What is given up, stated plainly: no infinities or NaN (a spreadsheet wants `#NUM!`, not a quiet NaN), no DPD bit layout, and **no quantum** — `1.50` and `1.5` are one value. The last is not a regression but a requirement: two representations of one number would be two canonical encodings and two state hashes, which DP-A4 forbids. Trailing-zero display is a number-format concern, and formatting never feeds back into values (docs/04).
Alternatives rejected: **(a) a fixed-point crate** — the popular ones carry a 96-bit mantissa (~28 digits), *fewer* than both this type and real decimal128, so it would not deliver the name either, and it would put a third party in the middle of a canonical op encoding that DP-A4 freezes for the life of the format. DP-B9 says never outsource the op algebra or its encoding. **(b) full IEEE decimal128** — correct but unjustified now; nothing yet requires bit-level interchange with another decimal128 implementation.
Repayment trigger: if XLSX round-trip or an external system demands true decimal128 bit-encoding, revisit — the representation is behind `Value::Decimal` and the canonical encoder, so the change is localised. Filed as TD-12.
Naming discipline: the code calls the type `Decimal`, never `Decimal128`, and the module doc states what it is not. A type that claims a standard it does not implement is a defect.

**D-041 — Excel's "15-digit" quirk is two rules, not one, and only one of them is validated.**
Implementing it as a single 15-significant-digit rounding did not reproduce `=0.1+0.2-0.3 → 0`, because that case is *catastrophic cancellation*, not display precision. Split into `compat_round_15` (display: `0.1+0.2` shows as `0.3`) and `compat_final_adjust` (evaluation: a result vanishingly small next to its operands is zeroed, which needs the operand magnitude and so cannot be a unary function of the result). `strict` applies neither.
~~**Evidence status:** `compat_final_adjust`'s `1e-15` relative threshold is Excel's *documented* behaviour, not oracle-captured … Filed as TD-13.~~
Implementation note: `compat_round_15` is a format-and-reparse round trip, not a scale-round-unscale. Scaling is the obvious approach and it is wrong at the extremes — `f64` holds powers of ten exactly only to `10^22`, so a built-up factor rounded `1e300` to `9.999999999999978e299`. Rust's float formatter and parser are pure-Rust, locale-free and in `core`, making the round trip both exact and identical on every platform (DP-A2).

**AMENDED 2026-08-08 by the first oracle corpus (docs/50, ADR-024). TD-13 is CLOSED, and the amendment corrects the decision rather than confirming it — the threshold as recorded was wrong, and there are three rules, not two.**

*(i) The cancellation threshold is **8 ULP of the larger operand**, not `1e-15` relative.* Let `e = floor(log2(max(|op1|,|op2|)))` over the operands of the final add/subtract. The result is zeroed **iff `|result| < 8 × 2^(e-52)` = `2^(e-49)`** — strict, so exactly 8 ULP is *kept*. Equivalently: zero when the top 49 bits of significance cancelled.
The relative rule is not merely imprecise, it is unable to reproduce the data: `=1+1E-15-1` (relative residue 1.11e-15) is zeroed while `=1000000+1E-9-1000000` (relative residue 1.05e-15) is kept. The binade sweep settles it, because inside a binade a fixed ULP count has a relative residue that halves from bottom to top, so the two candidate rules **cross over** — operand 1.0 at 7 ULP (relative 1.554e-15) is zeroed while operand 1.9 at 8 ULP (relative 9.35e-16) is kept. A smaller relative residue kept, a larger one zeroed; no relative threshold at any value orders those two correctly. Holds at both ends of six binades from 2^-10 to 2^49, 20 paired probes, no exceptions. The `G1 = 2-2^-52` block pins the scale to the **larger** operand's binade rather than the first operand's. Corollary worth stating alone: **Excel cannot subtract two adjacent doubles** — `=2-G1` is `0`.
*(ii) The operator rule is **positional**.* It applies to a formula's *top-level* result, not to the subtraction. `=0.1+0.2-0.3` is `0`, `=(0.1+0.2-0.3)` is `5.55e-17`, and `=1/(0.1+0.2-0.3)` is `2^54`. Parentheses around the *subtraction* suppress it; parentheses around an *operand* do not (`=(H1)-A1` is still zeroed). The zero is real once stored in a cell (`=1/A1` → `#DIV/0!`), and association matters: `=7*2^-52+A1-A1` is `0` but `=A1-A1+7*2^-52` is not. Both conditions are required — the final operator must be `+`/`-` *and* something must have cancelled.
*(iii) There are **two mechanisms**, and D-041 as written described one.* `SUM` and `AVERAGE` adjust **unconditionally**: their zero survives nesting, where the operator's does not. `=1/SUM(A1,7*2^-52,-A1)` is `#DIV/0!` while `=1/(A1+7*2^-52-A1)` keeps the residue; `=SUM(A1,7*2^-52,-A1)*1E17` is `0` while the operator form gives `155.43`. Same 8-ULP threshold, different activation condition. **An engine must implement both** — reproducing only the positional rule leaves `SUM` wrong in *every* nested position, which is the finding most likely to be missed because it is invisible unless you nest the aggregate.
Not established, and left open rather than guessed: whether `SUMPRODUCT`/`SUBTOTAL`/`AGGREGATE` carry the unconditional adjustment (the probe multiplied instead of summing, so it proved nothing), and whether the threshold shifts for opposite-sign operands more than one binade apart.

**D-081 — There is a *third* 15-digit rule, in the parser, and the engine does not implement it (new debt TD-32).**
Excel truncates a numeric **literal to 15 significant digits at parse time, destructively**, before the evaluator ever sees it: `=123456789012345678` is *stored* as `=123456789012345000`, and `=9007199254740992` — exactly representable, being 2^53 — is stored as `=9007199254740990`. The parser's exponent range is also narrower than a double's: `=1E307` parses, `=1E308` and beyond are **rejected outright** (though `Range.Value2` accepts `1.798E308` happily), `=1E-308` is accepted and silently stored as `=0`, and negative zero is normalised away.
Nothing in docs/12, docs/32 or D-041 mentioned this, and it was found only because the capture harness records what Excel *stored* alongside what it *computed* — 78 of 1126 cases carry a `stored_formula`. Named `compat_parse_15` for symmetry with the other two. It belongs in the lexer, not the evaluator, and it is destructive, so it cannot be layered on afterwards as a display concern. Filed as **TD-32** rather than implemented immediately: it changes the meaning of authored text under `Profile::Compat` and is worth doing with the conformance runner watching.
Rejection is conformance data, not a gap: those vectors carry `observed_status: "rejected-by-excel"` with Excel's own parser error, and our parser has to match.

**D-082 — `LEN`/`LEFT`/`MID` count Unicode scalars, and this is now a recorded non-divergence: do not "fix" it.**
Common wisdom says Excel is UTF-16, which would make `functions.rs`'s `chars().count()` wrong in every string function. Three independent routes into the oracle — a `UNICHAR()` formula, a cell seeded with Unicode scalars, and a cell seeded with an explicit UTF-16 **surrogate pair** — all disagree with the common wisdom: `LEN` of an astral character is `1`, `LEFT(emoji&"x",1)` returns the whole emoji, `FIND("x", emoji&"x")` is `2`, and `EXACT(scalar-seeded, pair-seeded)` is `TRUE` (Excel folds the pair into one unit).
Recorded as a *decision* precisely because it is a non-change. A future reader who knows the UTF-16 folklore and does not know this measurement would "correct" the engine and thereby **create** a divergence where none exists — the single most expensive kind of well-intentioned edit. No normalisation is applied either (`EXACT(é, e+combining acute)` is FALSE), which the engine also already matches.

**D-042 — Row 5 ships six of the lattice's variants; the rest land with the rows that need them.**
BOOTSTRAP row 5 enumerates `Blank/Bool/Number/Decimal128/Text/Error(+origin)`, while docs/04's full lattice also lists `Date`, `DateTime`, `Duration`, `Array`, `Reference`, `Rich` and `Lambda`. Following the build order rather than the destination: the six are implemented now, the rest arrive as additive variants (docs/10 evolution rule) with the rows that need them — dates with the date functions in row 6, `Array` with spill, `Reference` with the dep graph. Recorded so the gap reads as sequencing, not oversight.
`Origin` follows the same rule: it carries `Authored`, `Coercion`, `Arithmetic` and `Propagated` now, and row 6 extends `Propagated` with the source cell once formulas can reference one. A full provenance *chain* is deliberately not stored per value — that belongs in a watermarked fold over the log (DP-A9), not inline in every cell.

### Session 5 (2026-08-07) — Row 6, the formula engine

**D-043 — Dates are serials in the `Number` domain for now; `Value::Date` waits for the format layer.**
docs/04 lists `Date`/`DateTime`/`Duration` in the lattice and the archive says "dates are real types, not serial numbers". Row 6 nonetheless implements `DATE`/`YEAR`/`MONTH`/`DAY`/`WEEKDAY` over serial numbers, because a `Date` type is only distinguishable from a serial *once a number format exists to display it*, and there is no display layer until Q2. Excel itself stores a date as a serial plus a format, so serial-now is also the compat-correct representation.
Crucially this is **not** a semantics trap: when `Value::Date` arrives it coerces to its serial, so `YEAR(x)` keeps meaning what it means today and no stored formula changes result. That is the property that made this the low-risk order; had it not held, the type would have had to come first.
The 1900 leap-year fiction lives in the serial↔calendar conversion, not in the type — `Compat` reports serial 60 as 29 February 1900 and `Strict` does not, so the two profiles' serials differ by one from 1900-03-01 onward. That divergence is docs/32's intent, and it is pinned by `compat_reproduces_the_1900_leap_year_fiction`.

**D-044 — Approximate-match lookup is refused, not approximated.**
`VLOOKUP(...,TRUE)` and `MATCH(...,1|-1)` return `#N/A` rather than a guess. Excel's approximate match is only correct on a *sorted* key, and nothing in v0.1 can verify sortedness. A binary search over unsorted data does not fail loudly — it returns a confidently wrong number, which in a financial model is worse than an error. Exact match is implemented and correct; approximate arrives with the sortedness contract it needs. Filed as TD-14, since it is a real compat gap for imported workbooks.

**D-045 — Dispatch is a `match`, not the declarative registry docs/12 describes.**
docs/12 specifies registration carrying arity, per-argument coercion class, volatility tier, spill shape and an i18n block. At 60 functions that table would be scaffolding with nothing yet loading it — no spill engine, no localisation layer, no volatility scheduler. What the design actually requires *now* is preserved: names are canonicalised to English at parse time so localisation stays a view concern, and volatiles are injected rather than read. Build the registry when Core-200 and the spill overlay make it load-bearing.

**D-046 — `^`, `SQRT` and friends are implemented in-crate rather than via libm.**
The kernel is `no_std` (DP-A3) and DP-A2 demands bit-identical results on every target forever. Platform math libraries disagree in the last bits and change between versions, so `powf` uses exact repeated multiplication for integer exponents — the overwhelmingly common spreadsheet case — and a series expansion of `exp(y·ln x)` otherwise; `SQRT` is Newton's method. Accuracy for fractional exponents is therefore "good to ~1e-12", not "correctly rounded". Filed as TD-15 with the oracle corpus as the trigger to tighten it.

### Session 6 (2026-08-07) — Row 7, the dependency graph

**D-047 — A self-overlapping formula group is partitioned by column before falling back to singletons.**
Members of one R1C1 pattern can depend on each other: `=A1+1` in B1 and `=B1+1` in C1 render identically, so they group together, and evaluating them against one snapshot would silently compute a stale answer. The obvious fix — split any self-overlapping group into singletons — was implemented, measured, and found catastrophic: a chain of ten derived columns became **100,000 nodes for 100,000 cells**, destroying the grouping win in the most ordinary model shape there is, and the O(n²) edge build then hung outright.
Partitioning by column first makes a horizontal chain one group per column, each reading only the column to its left. Only a partition that still overlaps itself — a vertical running total, which is inherently serial anyway — falls back to singletons. Measured result: 10 nodes for 100,000 cells.

**D-048 — Dirtiness is a rectangle inside a group, not the group.**
The first implementation marked whole groups dirty. With 10,000-cell groups a single-cell edit recomputed all 100,000 cells in 53 ms against docs/31's 8 ms budget — a 1× speed-up over full recalculation, i.e. no incremental behaviour at all. Marking and evaluation now carry a `Rect`, and only members inside it are evaluated: 10 cells, 0.191 ms, 278× faster than a full pass.
A second cost surfaced immediately: answering "which members read this rectangle" by re-walking 10,000 member ASTs cost 10.5 ms on its own. Each member's read **bounding rectangle** is now precomputed at build time. A bounding box is a safe over-approximation — it can add an evaluation, never miss one — which is the correct direction for a dirtiness test.

**D-049 — Dependency edges come from the range index, never from pairwise comparison.**
Comparing every dirty group against every other is O(groups²), and it is what actually hung the first benchmark run. The index already answers "who reads this rectangle"; edges now use it. This is also the shape docs/13 describes — a stab, not a materialised edge set.

**D-050 — Cycles are read off the level assignment rather than from a separate Tarjan pass.**
docs/13 names Tarjan SCC on the dirty subgraph. Kahn's algorithm already produces the same fact for free: whatever it cannot place has no valid level, and by definition is in a cycle. Self-references are detected directly, since a group reading its own output produces no edge to detect. Adding a second traversal to learn something the first already proved would be cost without information. If cycle *reporting* later needs the SCC membership (docs/36's workbook health report groups cells by cluster), add Tarjan then — it is a reporting need, not a correctness one.

### Session 10 (2026-08-08) — TD-22 closed; Row 10 sync

**D-063 — The formula registry is a stamped LWW register, seeded by the replay pre-pass (TD-22 closed).**
D-056 made formula-vs-value depend on *application order*, which is correct only under full replay. Every mutation is now `max` over `(lamport, op id)` with the winner's payload kept — commutative, associative, idempotent — so the answer is a function of the op set alone. Proven over all 120 permutations of a five-write history (`registry_is_order_independent`).
The design problem was that order-independence needs a *value* write to leave a stamp, and a stamp per written cell is exactly the per-cell metadata ADR-005 exists to avoid (~480 MB at 10M cells). Rejected. Instead the registry holds entries only for cells some `SetFormula` names somewhere in the log, and that set is computed by the pre-pass that already decides tile promotion — one traversal, one timing constraint, the same argument applied twice: pay per-cell costs only where per-cell decisions happen. Shadowed entries are skipped by `iter()`, so the state hash is byte-identical to the pre-TD-22 behaviour — the unchanged replay hashes prove it.
**What this does *not* close:** the tile store and the axis tombstone set are still order-dependent, so `State` is not yet incrementally appliable. That was true before and is now the *only* remaining barrier rather than one of two. Filed as TD-24.

**D-064 — docs/27 §1 has four undefined edges; implemented exactly, gaps filed rather than invented.**
Building the machine transition-for-transition surfaced pairs a real link produces that the specification does not define: transport loss during `HELLO_SENT` or `BACKOFF`; a duplicate `InSync` after the session already reached LIVE; ops offered as `Give` while LIVE (or as `Ops` while SYNCING); an `Ack` arriving outside LIVE/SYNCING. Widening the machine would have been the easy move and the wrong one — docs/27 is normative and says an unlisted pair is a `debug_assert`, not a hint to improvise.
So the machine implements exactly what is listed, and the **shell** (`Replica::receive`) refuses to hand it an undefined pair: duplicates are dropped, one payload is routed to whichever of `Give`/`RemoteOps` the current state defines, and a handshake that dies is torn down and rebuilt from `DISCONNECTED`. Discarding a *protocol* message is safe because the next anti-entropy round re-derives it; a *local* op is never what gets discarded, which is the queue's job. Recommendation to the owner: docs/27 §1 should gain the four edges explicitly. Same precedent as D-062 — surface, do not self-amend.

**Second addendum — the `debug_assert` has now caught two shell bugs, which is the argument for transcribing rather than widening.** After the teardown branch was fixed, the benchmark harness gained a `partition`/`heal` pair, and `heal` called `connect` — a transition listed only from DISCONNECTED — on a replica sitting in BACKOFF. The assert fired on the first run of the new test. Had the machine been widened to "accept `Connect` from anywhere" (the tempting simplification when an unlisted pair first bites), both this and the HELLO_SENT wedge would have been silent behaviour changes instead of failures. Keeping the machine narrow moves the cost from *debugging a divergence* to *fixing a caller*, which is the trade worth having.

**Addendum — the teardown branch was documented before it was built, and W-SYNC-RELAY caught that.** The first implementation of "loss outside LIVE/SYNCING" did *nothing*, with a comment claiming an existing backoff timer would drive the next attempt. No such timer exists once a retry has fired, so a replica that lost its link mid-handshake wedged in HELLO_SENT permanently. At 2 replicas this is invisible; at 50 replicas and 4,051 dropped frames the run diverged and the mid-run kill delivered 1 of 117 queued ops. `Replica::hard_reset` now builds the fresh session the comment had promised, carrying the durable log and every unacknowledged op across, and `Replica::resume` reconnects by asking the state which transition is listed rather than assuming. **The lesson is about the comment, not the code:** a documented remedy that no test exercises is a claim, and this one was false for as long as nothing pushed the protocol hard enough to need it.

**D-065 — v0.1 transport is length-prefixed frames over loopback TCP, not WebSocket.**
docs/15 names WS. A WS client+server is ~20 crates (HTTP parsing, SHA-1 handshake, URL, RNG) against a workspace ceiling of 40 that stands at 10 (DP-S2), and DP-B9 forbids a second hashing stack. The sync *semantics* are transport-independent and fully proven, and docs/20 puts transport at L3 where it "changes transport never semantics". The swap touches `frame.rs` and `main.rs` and nothing else. Debt: TD-27. Rejected alternative: hand-rolling the WS handshake — that is custom crypto by another name.

**D-066 — `Op::decode` exists, and BOOTSTRAP row 2's proof claim was overstated until now.**
Row 2's proof line reads "encode/decode round-trip tests". There was no decoder: nothing had ever needed to read an op back, so the round-trip half of a canonical-encoding claim had never been tested. A socket needed it, and writing it found the shape of the gap rather than a bug — the encoder was correct. Decoding is total (every malformed input is a named error, never a panic), every truncation of every op variant is tested, and a non-canonical decimal is *repaired* on the way in so a hostile peer cannot smuggle a second spelling of one value past DP-A4. Unknown op tags are an error rather than preserved-opaque, because this encoding carries no length to skip over — DP-A5's forward-preservation rule needs a framed encoding, filed as TD-25.

**D-067 — A recovered session must adopt its own durable counter.** Found by W-SYNC-RELAY, not by a test: a replica rebuilt from its op log kept minting from counter 0 and re-issued ids it had already spent. Two different ops sharing one `(actor, counter)` made the log's dedup discard the second, and the replicas diverged. `integrate_batch` now advances the mint past any op it sees from its own actor. The benchmark caught what seven convergence tests did not, because only the benchmark restarts a replica that had already authored work.

### Session 20 (2026-08-09) — TD-34 paid: criteria coerce, lookups do not

**D-107 — The criteria sub-language is a *separate* comparison from the lookup one, and the corpus is what proves it.**

W-ORACLE **85.7% → 87.0%** (+18 cases). `COUNTIF`, `COUNTIFS`, `SUMIF`, `SUMIFS` and `AVERAGEIF` reach 100% but for the three cases TD-50 now owns.

The natural implementation — and the one that was there — reused `values_equal` for both families. That is wrong, and only measurement says so:

* **`COUNTIF(range, 7)` counts a cell holding the text `"7"`.** So does `COUNTIF(range, "7")`. A lookup for `7` does *not* find that cell, and `VLOOKUP("7", …)` finds it only because both sides are text. Criteria coerce across the text boundary; lookups compare within it. One predicate cannot do both, so there are now two.
* **`""` is the blank cell, and `"<>"` is every non-blank one.** Neither is a comparison against the empty string. Getting this wrong fails in opposite directions at once — `COUNTIF(C1:C5,"")` returned 0 where Excel says 1, and `COUNTIF(C1:C5,"<>")` returned 5 where Excel says 4.
* **Wildcards apply, and only to text.** `COUNTIF(range,"*")` counts the text cells and nothing else — not the numbers, not the blanks. The matcher itself came free from TD-35, which is why this cluster cost so little.
* **`COUNTIFS`/`SUMIFS` refuse criteria ranges of differing shape** rather than zipping to the shorter one. The pairing would be silently wrong, not merely short.

**Filed rather than bodged: TD-50.** `SUMIF(A1:A5,">25",H1:H3)` must sum `H1:H5` — Excel reshapes the sum range to the criteria range's dimensions from its top-left, so even `H1` alone means `H1:H5`. It cannot be implemented here, because an `Operand::Range` carries *values* and not the reference they came from: a three-cell operand simply has no `H4` in it. That is the same missing information TD-16's implicit intersection waits on, so the two are filed to be repaid together rather than one of them being faked now.

### Session 20 (2026-08-09) — TD-14 and TD-35 paid: the lookup algorithm is the one Excel runs, not the one it documents

**D-106 — Approximate match is implemented as Excel's binary search, and the wildcard sub-language is one matcher shared by every function that has it.**

W-ORACLE **83.5% → 85.7%** (+31 cases). `VLOOKUP`, `HLOOKUP`, `XLOOKUP`, `MATCH`, `FIND` and `SEARCH` all reach **100%**.

**Why the old refusal (D-044) was right, and what changed.** TD-14 refused approximate match because Excel's contract requires a sorted key and v0.1 could not verify sortedness — a binary search over unsorted data returns a confidently wrong number. That reasoning still holds; what changed is that the oracle now says *which* wrong number, and reproducing Excel means reproducing it. Over the unsorted key column `30, 10, 50, 10, (blank)`, `VLOOKUP(35, …, TRUE)` returns the row holding **10**: the search probes the middle, finds 50 above the needle, halves downward and lands there. A linear "largest key ≤ 35" scan answers 30 — defensible, documented, and not what Excel does. **This is the clearest case yet for ADR-024's premise that the binary is the spec**: the correct behaviour is not derivable from the contract, only from the implementation, so the debt could only be paid after the capture existed. The refusal was the right call for eleven sessions and the wrong one the moment vectors landed.

**`XLOOKUP` deliberately does not binary-search.** Its `-1`/`1` modes take the nearest candidate anywhere in the vector, which is why XLOOKUP is safe on unsorted data and VLOOKUP is not. Two different algorithms behind two similar-sounding arguments — measured, not assumed, and worth stating because unifying them would have been the natural refactor and would have been wrong.

**One matcher, three call sites.** `*`, `?` and `~`-escape are implemented once and shared by `SEARCH`, the exact-match lookups and (next) the criteria sub-language. Two things the corpus forced:
* The matcher is **iterative with a backtrack point, not recursive** — a `no_std` kernel evaluating a hostile formula must not be able to blow its stack on `"*a*a*a*…"` (DP-E2).
* The escape has to work on **both** paths. `a~*c` has no *active* wildcard, so it takes the literal path — and the literal still needs its tilde stripped before comparison, or the engine searches for a tilde and returns a silent `#N/A`. Both `VLOOKUP("a~*c", …)` and `SEARCH("~*", "a*b")` failed on exactly that.

**Two smaller measured rules taken with them.** `MATCH` refuses a range that is neither a row nor a column (`#N/A`) rather than scanning it row-major and returning a confident wrong ordinal; and a **blank lookup value matches nothing**, because Excel reads the empty cell as 0 — so `MATCH(A1, …, 0)` over a column containing blanks is `#N/A`, not the position of the first hole.

**Left open on purpose.** Three `INDEX` cases still diverge, and all three are **TD-16** (implicit intersection needs the calling cell's row and column, which arrives with the dependency graph). `INDEX(range, 0, n)` now correctly returns the whole column — `SUM(INDEX(A1:B5,0,1))` is 150 — but collapsing that array in a *scalar* context still takes the top-left where Excel intersects against the caller. Attributing those to TD-14 would have overstated this row.

### Session 20 (2026-08-09) — TD-33 paid: the date system is a workbook property, not a profile

**D-105 — Excel's two date systems are modelled as an explicit `DateSystem` on the evaluation context, and every rule in them is oracle-measured.**

TD-33 was the largest cluster in the W-ORACLE table (~98 cases plus 104 of the 130 1904 cases). Paid: **74.2% → 83.5% overall**, with the 1904 corpus going **20.0% → 87.7%** and `DATE`/`DAY`/`MONTH`/`WEEKDAY`/`YEAR` reaching **100% in both corpora**.

**Where it lives, and why not on `Profile`.** `Profile::{Compat,Strict}` says *how faithfully to reproduce Excel*; the date system says *which calendar this workbook uses*. They are orthogonal — a 1904 workbook still wants compat coercion — and the file format agrees: `workbookPr/@date1904` is a per-workbook property. So `DateSystem` is a third axis on `Context`, defaulting to 1900, and `usk-calc`'s `Engine` carries it beside `profile` so a recalculated 1904 workbook does not silently shift every computed date by 1,462 days.

**The rules, none of which follows from the others** (docs/50 finding 6 said there were five; the corpus shows six):

1. **Serial 0 is a position, not an error.** 1900 calls it "1900-01-00" — `DAY(0)=0`, `MONTH(0)=1`, `YEAR(0)=1900`. 1904 calls it 1904-01-01, a real date with `DAY(0)=1`.
2. **Serial 60 is 1900-02-29**, the Lotus phantom. Reproduced, because otherwise every date in every imported file shifts by a day.
3. **Years 0–1899 mean 1900+year.** `DATE(1899,12,31)` is in the 38th century. The offset applies to the *argument*, before month rollover — which is why `DATE(1900,0,1)` lands in December 1899 and is `#NUM!` rather than being rescued by it.
4. **Months and days roll over** rather than erroring, and the day rollover happens **in serial space**, so an index crossing the phantom picks it up. That one choice is why `DATE(1900,2,29)=60` and `DATE(2024,1,32)=45323` need no separate rules.
5. **The serial range is closed at both ends**: 0..=2,958,465 in 1900, 0..=2,957,003 in 1904 — 9999-12-31 in each.
6. **`WEEKDAY` is `serial mod 7`, not the true weekday.** In 1900, serial 1 reports Sunday where 1900-01-01 was really a Monday, because the phantom has not been inserted yet at that point in the sequence. Consulting the calendar instead would have made serials 1–59 disagree with Excel. Return types are 1/2/3 and 11–17; **0 and 4–10 are `#NUM!`**, a gap in the numbering that only measurement would have found.

**The 1904 offset is 1,462, not 1,461** — four years between the epochs, plus the day the 1900 system counts that never existed. The constant falling out of the phantom rather than being pasted in is what makes the two systems one model.

**Deliberately not done: locale date text.** `YEAR("2024-03-15")` is implemented; `YEAR("15/03/2024")` is not, although its fixture is in the corpus. That string means 15 March here and 3 December on a US host, so implementing it from this capture would encode one machine's regional settings as engine behaviour — the exact failure an oracle exists to prevent. Filed as **TD-49** with the condition that would clear it (a locale model, or a second capture on a differently-configured host), per D-104's rule.

**The corpus tells the runner which system it is**, read from `_index.json`'s `provenance.date_system` rather than from the directory name, and a corpus that does not say is a hard error. A mislabelled folder would otherwise turn 104 real divergences into an invisible pass.

### Session 20 (2026-08-09) — TD-47 was false, and the register has now produced the same defect twice

**D-104 — `gates.ps1` is 5.1-compatible and always was. The debt entry accusing it was written from a true fact about the shell and never run against the script.**

TD-47 asserted that `tools/gates.ps1` "requires PowerShell 7 and aborts on a Windows PowerShell 5.1 host". Measured on this host (Windows PowerShell **5.1.26100.8875**, the only PowerShell present — `pwsh` is not installed): the script runs top to bottom in **one invocation, every gate green, exit 0**. Verified in all three ways it is ever invoked — bare `powershell -File`, with every stream redirected to a file, and dot-sourced inside a `Stop`-preference session.

**The mechanism TD-47 names is nevertheless real, and was reproduced rather than taken on faith.** Under `$ErrorActionPreference = 'Stop'`:

* `cargo clippy -p usk-types --all-targets -- -D warnings` — exit 0, no throw.
* the same command with its stderr merged into the pipeline — **`NativeCommandError`**, thrown purely because cargo prints `Finished ...` to stderr.

So 5.1 wraps a native command's stderr in an `ErrorRecord` **only when that stderr is merged into the PowerShell pipeline**, not merely when it is written. `gates.ps1` never merges it: stderr goes to the console and every native command is judged by `$LASTEXITCODE`. The trap is therefore **latent — one redirection operator away — and was never armed**.

**Rejected: install PowerShell 7.** The obvious reading of the repair instruction, and wrong twice over. It is a machine-wide MSI needing elevation, which DP-S5 and CLAUDE.md's workspace boundary both bar; and it would have "fixed" a script that already worked, leaving the real hazard (the latent redirection) in place and unmeasured.

**Taken instead: two gates where the assumption was.** A runtime probe asserting that a native command which writes to stderr and exits 0 does not derail the run, and a static grep refusing any stderr-into-pipeline redirection in `tools\*.ps1`. Both run first and cost milliseconds, so an incompatible shell is named in two seconds instead of three minutes into a cargo build. The grep is the one that matters: it makes re-arming the trap a gate failure rather than a silent regression.

**The defect this is really about is the register, not the shell.** TD-47 is the *second* row to assert an unverified host condition that measurement then refuted — TD-48 (filed in session 18 under TD-28's number) was the first, and D-078 already drew the lesson: *a status note must name the condition that would clear it, or it ages into a false statement.* D-078 was not enough, because both rows named a clearing condition and neither was ever **run**. So the rule is strengthened:

> **A debt row that asserts something about this host is not filed until the command that demonstrates it has been executed and its output pasted into the row.** An assertion derived from a true general fact is a hypothesis, and hypotheses go in the row as hypotheses.

Register IDs are also confirmed **append-only**: a paid row is struck through and keeps its number forever. TD-28's second occupant is re-filed as TD-48 in docs/44, because a vacated-looking ID is what invited the reuse in the first place.

### Session 19 (2026-08-09) — where the stamps have to live: an ADR-level fork, not written

**D-103 — Implementing the stamp-carrying image needs an ADR-005 amendment, so it is NOT implemented here. The fork is stated with both costs measured.**
D-102 settled the *encoding* (delta-varint, 3.1 B/cell, 153.2 MB at 10M — passes A-001). Attempting the implementation surfaced a second question the encoding does not answer: **where do the stamps come from at the moment an image is written?**

A freshly-replayed `State` does not have them. That is not an oversight, it is ADR-005: a summary tile keeps *no* per-cell metadata, which is the entire reason a 10M-cell workbook fits its budget (TD-09 measured 8.4 → 74.5 B/cell when it did not). So an image writer has nothing to serialise. The three ways out, and what each really costs:

**(a) Keep stamps resident for non-promoted cells.** Simple, no dilemma, and the image delta-varints them on the way out. Measured cost: per-tile writer table plus a dense `(lamport, counter)` pair is **17 B/cell**, taking the collab pattern from **123.6 → ~285 MB** at 10M. It passes A-001's 400 MB bar and consumes most of the headroom — and the deeper problem is that *if every cell carries a stamp, promotion stops meaning anything*. `PromotionStats::promoted_cell_fraction` and A-002's amplification bar both become vacuous, and ADR-005's summary tile stops being a memory optimisation. **That is an ADR-005 amendment, not an implementation detail.**

**(b) Reconstruct stamps at snapshot time from the log.** No resident cost — the container has the ops when it compacts. But materialising a cell→stamp map for 10M cells is ~320 MB of *temporary* peak on top of the state. A-001 measures "RSS at load", so this is arguably outside its bar; reading it that way to make the number pass would be exactly the convenient interpretation D-062 established we do not take. It can be bounded by streaming per tile band, which costs a re-sort of the op stream.

**(c) Restrict adoption to the cases that need no stamps** — a tail that touches no cell already present under a different author. Sound, small, and it degrades to a named refusal. It does not help, because the fallback for a refusal is "replay the ops the snapshot covers", and those are exactly the ops compaction pruned.

CLAUDE.md's rule is that irreversible or expensive-to-reverse decisions get an ADR **before** implementation, and (a) — the only option that is simple — retires a frozen ADR's central claim. Writing 250 lines of stamp plumbing in the last of a session, against an architecture decision nobody has taken, is how a frozen ADR gets amended in a commit message.

**So the tree is left green with the image built, measured and unwired.** What is now *known* rather than open: the encoding (D-102), the ordering guard needed either way (D-101), and the fact that the remaining question is about ADR-005's memory model rather than about serialisation.

**Recommendation for whoever writes the ADR:** (b), streamed per tile band. It keeps ADR-005's claim intact, keeps A-001's headroom, and pays its cost during compaction — which is background work with a natural place to be slow — rather than during load, which is the thing docs/31 budgets. (a) is the tempting one and it quietly deletes a differentiator.

### Session 18 (2026-08-09) — the stamp-carrying image, measured

**D-102 — A stamp-carrying tile image fits A-001, but only if the stamps are delta-varint encoded. Measured, not argued.**
TD-46 priced per-cell winner stamps at "24 B/cell — the memory TD-09 removed" and left the choice open. `tools/image-bench` (workload **W-IMAGE-STAMPS**, docs/38) measures it on the real W-TILE-10M corpus, and the answer depends entirely on the encoding:

| stamp encoding | B/cell | 10M sidecar | total vs A-001's 400 MB |
|---|---:|---:|---|
| naive, as it sits in memory | 32.00 | +305.2 MB | **428.8 MB — FAIL** |
| per-tile writer index + `u64` pair | 17.00 | +162.1 MB | 285.7 MB — pass |
| **writer index + delta-varint** | **3.10** | **+29.6 MB** | **153.2 MB — pass, 2.6× headroom** |

So the entry's own estimate was the one arrangement that fails, and it fails by 7%. It is also the arrangement nobody would ship: within a tile a bulk write assigns lamports and counters that ascend almost in lockstep, so each delta is a single varint byte and the writer is a one-byte index into a per-tile table. Measuring the thing you would actually build, rather than the thing that is easiest to estimate, moved the answer from "no" to "yes with room to spare".

Per-cell figures are **scale-stable** — collab 3.10 → 3.12 B/cell from 1M to 2M cells — so the projection to 10M is a projection of a flat number, not an extrapolation of a trend. The adversarial pattern drifts (7.95 → 9.00) because a 50%-contested history deltas badly; docs/38 sets no RSS bar there, and its cells are already promoted, so they carry their stamps in `Meta::Mixed` and need no sidecar at all.

Two conservatisms are stated rather than banked: the measurement counts **every** cell when only non-promoted ones need an entry, and a sidecar costs RSS only if it is *decoded* at load — kept encoded and decoded per tile as the tail reaches it, the load cost is the image's own bytes.

**One number worth recording on its own:** the image is *smaller than the resident state it encodes* — 9.59 against 11.33 B/cell at the collab pattern, and 68.43 against 137.80 at the adversarial one, where the tagged-union in-memory layout is far heavier than the packed serialised form. Whatever else the image changes, it does not trade size for speed.

**What this does not settle.** The ordering half of D-101 is untouched: a tail op canonically *earlier* than the image still cannot be placed, and the image must record its greatest canonical key so that case is refused rather than misplaced. TD-46 stays open as implementation work with its design question answered.

### Session 17 (2026-08-09) — the tile image, and why it is not yet the snapshot body

**D-101 — The tile image is built and proven; wiring it in as `snapshots.body` is blocked on a CRDT question, not on the format.**
docs/16 and docs/26 both specify the snapshot body as a "tile+object image", and `usk_state::image` now produces one: a materialised `State` — axis insertion trees, slot maps, tiles with their presence bitmaps and packed payloads, per-cell stamps and retained losers where a tile is promoted, and the stamped formula registry including its shadowed entries. It round-trips to the same `state_hash`, it is chunked per tile so unchanged tiles hash identically across snapshots (docs/16's "structurally shared via tile Merkle identity"), it is bounded on read, and a fuzz sweep over corrupted images cannot make it panic. Seven tests.

**It is deliberately not wired into `Snapshot`.** The blocker is worth stating precisely, because it is the kind of thing that gets re-discovered expensively:

An image throws away op ids. A **summary tile** — the 24-byte common case that makes ADR-005's memory argument work — carries no per-cell stamps, and it is correct only because `State::replay` applies ops in canonical total order: with one author per cell, a later op is the winner by construction and there is nothing to compare. Adopting an image and applying a tail onto it breaks that in two ways:
1. *Ordering.* A tail op canonically **earlier** than the image cannot be placed — there is nothing left to compare it against. This one is fixable: record the image's greatest canonical key and refuse (a remote op arriving after a snapshot was taken can genuinely be older).
2. *Retained losers.* This one is not. A cell first written inside the image and rewritten by the tail becomes multi-writer, so ADR-006 and DP-A8 require the earlier value to be **retained with its author and stamp** — and the image no longer knows either. Reconstructing them from the tile's summary `(max_lamport, writer)` would be an approximation, and `conflicts()` would then differ between a replica that restarted and one that did not. That is a divergence in exactly the "conflict honesty" property BOOTSTRAP lists as differentiator 3.

Preserving it needs a per-cell winner stamp for every *present* cell — 24 bytes/cell, which is ~24 MB at 1M cells and ~240 MB at 10M: the memory TD-09 removed. So the honest options are a stamp-carrying image (measurable, and it must be measured against A-001 before it is chosen), or restricting adoption to snapshots with an empty tail. Neither is a five-line change, and picking one on the way past would have been inventing an ADR-005 amendment in a commit message.

**What was reverted, and why it is recorded rather than silently undone.** The wiring was written and backed out: `Snapshot::of_state`, `VerifiedSnapshot::state()`, `Salvaged::base_state()` and a container that adopted the base and applied the tail. Also reverted: a `Watermark` carrying the *gaps* below each actor's max, which makes `covers()` exact and would have replaced the container's million-entry coverage set. It is a good idea and it does not survive the round trip — `snapshots.watermark`'s stored encoding is `(actor, counter)` pairs with no room for gaps, so a watermark read back off disk never equals one built in memory, and `verify` rejected every snapshot. The container test caught it. Recorded so the next attempt starts from "the encoding needs a version bump" rather than from the same afternoon.

**What did land beyond the image**: the container's snapshot-coverage set is a `HashSet` rather than a `BTreeSet`, worth about a second of the W-OPEN-1M cold open.

### Session 15 (2026-08-09) — Row 14, the MCP server

**D-095 — The `query` (SQL) tool is NOT shipped, and DataFusion is not added.**
BOOTSTRAP row 14 lists `query` (DataFusion) among the MCP tools, so its absence has to be a decision rather than an oversight. DataFusion's dependency closure is well over a hundred crates — Arrow, Parquet, sqlparser, tokio, and their trees — against a DP-S2 workspace ceiling of **40 that currently stands at 29**. It is not close, and TD-01 already prices the Arrow layer as H2 work.
What is shipped instead covers the questions `query` was for: `describe_sheet` answers "what is in this sheet" with per-column statistics, and `read_range` is the capped escape hatch for the rows themselves. What is genuinely lost is aggregation and filtering server-side, which an agent must now do itself over a bounded read. Filed as **TD-42** with the Arrow layer as its trigger, so it is repaid where TD-01 already says the machinery lands.

**D-096 — Cell text leaves the server only through `untrusted()`.**
docs/21 requires cell-derived text to be labelled untrusted in every response. Implemented as a single function that wraps a string in `{"untrusted": "..."}`, with **every** call site being a cell value, a formula source, a sheet name or a user-supplied label. A convention would have been a hope; a single chokepoint is greppable, and `every_cell_derived_string_is_labelled_untrusted` drives a cell containing "IGNORE ALL PREVIOUS INSTRUCTIONS" through `read_range` and `describe_sheet` to prove the envelope holds on both routes.
Numbers and booleans are deliberately **not** wrapped. A number cannot carry an instruction, and wrapping everything would train a reader to ignore the envelope — which is how a security marker becomes decoration.

**D-097 — A tool that declines returns a *result*; only a malformed request is a JSON-RPC error.**
An unknown tool or a missing `params` is a transport error (`-32601`/`-32602`). A tool that ran and said no returns a normal result with `isError: true` and a named refusal code. Conflating the two leaves an agent unable to distinguish "you asked wrongly" from "the server broke", and the second is the only one worth retrying differently.
Every refusal carries a machine-readable `code` (`version_mismatch`, `preview_required`, `preview_mismatch`, `edit_refused`, `out_of_range`, `growth_too_large`, `too_many_edits`, `invalid_arguments`) *and* a sentence explaining it, because the agent needs the first and the human reading the transcript needs the second.

**D-098 — The blast-radius gate is enforced by hash, not by honour.**
docs/21 makes preview-before-mutation a host guarantee rather than tool etiquette. `preview_edits` simulates against a scratch replay of the log and returns a `preview_hash` — the state hash the workbook *would* have. Above [`BLAST_RADIUS_PREVIEW_REQUIRED`] changed cells, `apply_edits` refuses without a **matching** one.
The matching is the part that matters: without it, "I previewed something" would satisfy the gate. `a_large_edit_is_refused_without_a_matching_preview_hash` asserts all three arms — absent hash refused, wrong hash refused, right hash accepted. A supplied hash is verified even when it was not required, because an agent that offers evidence should have it checked rather than ignored.
`expected_version` is the same idea for concurrency: the agent states the state hash it reasoned about, and a workbook that has moved refuses rather than applying an edit to a world the agent never saw.

**D-099 — `apply_edits` grows the sheet, within a bound.**
The end-to-end test found this on its first run: an agent's *first* edit lands on an empty workbook, `A1` does not exist yet, and the batch was refused. A surface that cannot accept the first edit is unusable at exactly the moment an agent starts working, and a spreadsheet grows when you type outside it.
Growth is emitted as ordinary `InsertRow`/`InsertCol` ops in the same batch, so it is attributable, replayable and undone with the rest of it (DP-A1) — and it is **reported** (`rows_added`, `columns_added`) rather than silent. It is also bounded: unbounded auto-growth makes `{"cell":"XFD1048576","value":1}` a denial of service costing the agent one line, so [`MAX_GROWTH_PER_CALL`] separates "the sheet grew to fit" from "the sheet was used as a weapon".

**D-100 — Agent undo is a batch journal in the MCP layer, not a change to the reducer.**
docs/21 asks for undo that is "agent-session-scoped" and for each `apply_edits` to be one reversible unit. `usk-reduce` pushes one undo group per command, so the MCP server keeps its own journal of `(label, group_count)` and `undo` pops exactly that many.
This is the right layer rather than a workaround: *agent-session scope* is an MCP concept, and putting it in the reducer would make every caller inherit an agent-shaped grouping. Atomicity comes from validating the whole batch against a scratch replay before applying any of it — the failure modes are all validation failures, so a batch either runs completely or does not start (`a_batch_with_one_bad_edit_applies_none_of_them`).

### Session 14 (2026-08-09) — Row 12's XLSX half

**D-090 — ZIP, DEFLATE, XML and XLSX are written in-house, and cost zero dependencies.**
XLSX is a ZIP of compressed XML, so reading one needs an inflater and an XML parser before any spreadsheet semantics appear. `flate2` brings a C library or `miniz_oxide`; a Rust XML crate brings its own tree. The workspace budget stood at 29/40 after `rusqlite` took nineteen slots (D-073), and DP-S1/S2 says one of each *hard* thing. **It still stands at 29/40** — the three decoders added nothing.
The argument is not "we can write anything ourselves". It is that these two formats are old, completely specified in short documents, and — crucially — **decoders whose correctness is checkable against files the world already has**. The corpora are generated by Python's `zipfile`, i.e. by an implementation that is not ours, because a decompressor tested only against its own compressor proves that two bugs agree. Same reasoning as D-083 (`usk-json`), D-046 (in-crate `powf`) and D-052 (seeded sweeps).
Split into three crates rather than one, per DP-C4: a container format, a markup format and a document format are different things to be wrong about, and each landed green before the next began.

**D-091 — The DEFLATE decoder is strict about Huffman trees, with exactly the two exceptions RFC 1951 requires.**
An under-subscribed Huffman code decodes ambiguously, which is how a decompressor is talked into reading memory that is not its own, so an incomplete tree is refused. Two exceptions are mandatory and both were found by the corpus rather than by reading:
* **The fixed distance table** is 30 codes of 5 bits in a 32-code space — incomplete *by construction*, because symbols 30 and 31 "will never actually occur". Applying the strict rule to it made **every ordinary compressed file fail to inflate**. It is normative, so it is not the decoder's place to reject it; a *dynamic* tree of the same shape still is, because there the shape is the stream's choice rather than the format's.
* **A single-symbol alphabet** is legal and is how a stream with exactly one distance code is encoded.
The lesson is about testing, not about DEFLATE: both exceptions are invisible to hand-built streams and unmissable against a real archive. `an_over_subscribed_tree_is_refused` and `a_single_code_alphabet_is_accepted_because_real_files_use_it` pin the two sides so the strictness is never tightened back over the exception.

**D-092 — XXE and billion-laughs are *unimplemented*, not disabled, and a `<!DOCTYPE` is refused rather than skipped.**
docs/24 says "DTD/external entities disabled". There is no code in `usk-xml` that resolves a DTD or an external entity, so the attacks are unreachable rather than switched off — the strongest version of that requirement and the cheapest, since the feature was never wanted. Only the five predefined entities and numeric character references expand, and neither can nest, so expansion is O(1) per reference.
A document carrying a `<!DOCTYPE` is **refused**, not skipped. Skipping would mean silently reinterpreting a document whose author asked for a feature we do not have, and disagreeing with the writer about what a file means is worse than declining to read it.
Related and deliberate: an element left open at the end of a document is a `Truncated` error, not a complete document with fewer children. A worksheet part cut short would otherwise look like a sheet with fewer rows — the silent partial read docs/16 forbids at the storage boundary, arriving at the import one.

**D-093 — The fidelity number counts data, not scope; quarantined and structural parts leave the denominator for different reasons.**
`Fidelity::part_coverage` is parts read ÷ parts that carry user data and are safe to read. Two exclusions, each earned:
* **Quarantined** parts (docs/24's active content). Not reading `vbaProject.bin` is the *correct* outcome; counting it as a miss would push the number down for doing the right thing.
* **Structural** parts — `[Content_Types].xml` and `_rels/.rels`. They carry no user data, so not reading them loses nothing.
The first version lumped both in and scored a workbook we read *perfectly* at 60%, which is not a fidelity number, it is noise. What stays in the denominator is `parts_ignored` — charts, drawings, pivot caches — because those **are** user data this build drops, and a coverage number that excused them would be measuring its own scope rather than the file. Measured: 19 of 20 corpus files at 100%, and `14-unmodelled-parts.xlsx` at 50% because it genuinely loses three parts.
Quarantine is also "we did not touch it" rather than "we touched it carefully": an active part's bytes are never decompressed, and the classification happens before any part is read.

**D-094 — Sheets are located through the relationship table, never by filename.**
`xl/worksheets/sheet1.xml` is a convention, not a guarantee: the workbook names a relationship id, and the id names the target. A reader that assumes sheet *N* lives in `sheetN.xml` silently returns the wrong sheet's data, which is the kind of defect that survives a demo. Corpus file `10-rels-out-of-order.xlsx` crosses the two over so the assumption cannot be made accidentally.
The one place a convention *is* used: a workbook whose relationship part is missing entirely falls back to `sheetN.xml` rather than dropping the sheet. Guessing beats losing data when the guess is Excel's own convention and the alternative is silence.

### Session 13 (2026-08-08) — Row 12, the CSV half

**D-085 — Injection neutralization is decided by *type*, not by leading character, and the rule differs by direction.**
OWASP's rule for CSV injection is "a field beginning `=`, `+`, `-`, `@`, TAB or CR is dangerous — prefix it". Applied literally it **mangles every negative number in the file**, which is a data-corruption bug introduced in the name of security. Both directions needed a refinement, and they needed *different* ones:
* **Export** neutralizes only `Value::Text`. We are writing from typed cells, so `Number(-1)` renders as `-1` and is never touched while `Text("-1+1")` is prefixed. Knowing the type is the advantage a spreadsheet has over a generic CSV writer, and this is where it pays.
* **Import** has no types yet — every field is a string — so the export rule cannot be reused. The refinement there is exact rather than heuristic: *a field that parses as a plain number is not a risk, because the formula it would become evaluates to that same number.* `-3` is safe; `-3+cmd|'/c calc'!A0` is not. The test uses the engine's own `coerce_input`, so it can never disagree with what the importer would actually store.
I got this wrong first: `commit` used the lexical rule and turned every negative number into text. `a_clean_table_survives_a_full_round_trip` caught it on the first run — the round-trip property found a bug that neither an import test nor an export test would have, because each half looked correct alone.
Neutralization also has an exact inverse (`strip_neutralization`), applied on import, so export→import is an identity for text values. The ambiguity that creates is real and inherent to CSV — a field authored as `'=x` is indistinguishable from a neutralized `=x` — and Excel resolves it the same way. A security fix that quietly rewrites data on every round trip would be a data-loss bug wearing a badge.

**D-086 — The type-inference preview reports *measured* loss, not pattern matches, and suggests only what cannot lose data.**
docs/24 demands the gene-name decision be surfaced. Two design choices make the surfaced thing worth reading. First, a field is flagged as lossy by **round trip** — render the inferred number back to text and compare — rather than by matching `\d+E\d+`. A pattern would flag `1E2` in a column that genuinely is scientific notation, and a warning that fires on correct data is a warning users learn to click through. Second, the *suggested* decision is only `Number` when nothing in the column loses information, so following the suggestion blindly can never mangle data. Excel's own answer is available and is called `PerCell` — the user has to ask for it.
The API shape carries the rule: `analyze` returns a report and commits nothing; `commit` requires an explicit `Decision` per column. The silent path does not exist to be taken by accident on a tired afternoon.

**D-087 — The parser subprocess is confined by a hand-written Windows job object, and the gap in that confinement is named rather than implied.**
docs/24's sandbox clause is *"no exceptions"*, so `ehkatra-io` has no in-process import function at all — the only way to import is `import_csv`, and it spawns. Confinement is applied **before the child is handed a single byte**; failing to apply it is a fatal `NotConfined` error rather than a warning, because a sandbox that silently degrades to no sandbox is exactly what the rule is written against.
Bindings are hand-declared `extern "system"` rather than `windows-sys` (~3 crates for six functions and one struct, against a budget at 29/40). What is enforced: address-space isolation, `JOB_OBJECT_LIMIT_PROCESS_MEMORY`, an active-process limit of 1, `KILL_ON_JOB_CLOSE`, a host-side wall-clock cap, an output cap, and a fresh process per document. What is **not**: a syscall filter, because Windows offers no seccomp equivalent without a driver or an AppContainer profile and DP-S5 forbids both. "No network" is therefore *structural* — the child links no networking code — and that is filed as **TD-37** rather than described as seccomp-equivalence.
Two smaller decisions that are load-bearing. The document travels on **stdin**, not as a path, so the child has no reason to touch the filesystem and no path to be confused about. And the parser binary is resolved **next to the current executable, never through `PATH`**: a sandbox is worth nothing if an attacker who can drop a file earlier in `PATH` chooses what runs inside it.

**D-088 — The host revalidates bounds the child already checked, and the IR has no verbs.**
docs/24 says *"IR-only output revalidated against schema by the host"*, and the reason is worth stating: the child has just processed a hostile file, so if it was compromised, its output is the attacker's output. Every `usk_csv` bound is therefore re-run against the decoded IR, and a violation is reported as `BoundViolated` — a child breaking a bound it was itself supposed to enforce is compromised or broken, and either way its output is discarded.
The IR vocabulary is deliberately narrow: records, a report, or a named error. There is no field in it that says "do this". The nearest thing to an instruction it carries is a column's suggested decision, and an unrecognised name falls back to `Text` — a compromised child cannot pick `Number` for a column by sending a name we do not know.

**D-089 — Fuzzing is a seeded generator plus an in-repo corpus, run by `cargo test`.**
`cargo-fuzz` is in the stack list and needs a nightly toolchain and a global install, which DP-S5 forbids on this host. D-052 already settled the shape: reproducible from a seed alone. What `cargo-fuzz` buys that this does not is coverage-guided mutation; what this buys is that **it runs in `cargo test`**, which means it runs — the property a solo project needs most (docs/07 §2).
The assertions are contracts, not "it does not crash": totality, chunk independence, downstream totality through `analyze`/`commit`, and writer/reader agreement. **It earned its place on the first run**, finding that the UTF-8 BOM strip only worked when the BOM arrived whole in the first chunk — split across a chunk boundary, `\u{FEFF}` became part of the first header name and every later column lookup failed for a reason invisible in a diff. The corpus lives in the repo (`crates/usk-csv/tests/corpus/`) so a document that once found a defect keeps being tested; a corpus in a temp directory tests the same bug exactly once.

**D-083 — JSON is written in-house (`usk-json`), not taken from `serde_json`.**
Three v0.1 surfaces need JSON: the conformance runner (docs/50's corpus), import/export reports (docs/24) and the MCP server's JSON-Schema I/O (docs/21). `serde` + `serde_json` is roughly six crates against a workspace ceiling of 40 that stands at 29 after `rusqlite` took nineteen (D-073) — 15% of the remaining budget for a grammar that fits on a postcard. DP-S1/S2 says one of each *hard* thing, and JSON is not one of the hard things. Same reasoning as D-046 (in-crate `powf` over libm) and D-052 (seeded sweeps over `proptest`); measured outcome: the workspace closure is **still 29/40** after adding it.
Writing a parser instead of taking one owes tests in exchange, and the ones that matter are the ones that bite: surrogate pairs (the corpus contains astral characters — docs/50 finding 5), escape round-trips, a bounded nesting depth because MCP input is agent-controlled (docs/37), and **numbers kept as source text**. That last is not fastidiousness: docs/50 measured a JSON reader moving `0.10000000000000009` by one ULP and producing six false failures in the capture harness's own validator. `Json::Number` holds the literal and `as_f64` parses through `core`, which is correctly rounded and locale-free — the same property DP-A2 leans on in `compat_round_15`.
Also fixed while here: `tools/dep-budget.mjs`'s kernel list was missing `usk-sync` and `usk-recover`. Harmless while both carry zero dependencies, but a budget that does not list a crate would not notice the day it grew one.

**D-084 — The first W-ORACLE run: 65.6% → 74.2%, and what the runner is allowed to count.**
The conformance runner exists because docs/32 makes Excel compatibility "a measured profile" and BOOTSTRAP's differentiator 7 promises the `compat` profile keeps Excel's quirks — claims that were, until now, intentions. The comparison rules are recorded in docs/38 as part of the workload, because changing them changes the number.
Three of those rules are deliberate refusals to flatter the result. **`near` is a fail**: a numeric answer within 1e-12 relative is counted separately so TD-15's last-bit accuracy is *visible*, and counted as a fail so it can never quietly become a pass. **Unjudged cases are reported, not skipped**: a percentage that silently drops what it cannot score is the easiest number in the world to make look good (the run reports 0). **`general_text` is not asserted**, so the headline is value conformance and not display conformance, and the omission is published with the number rather than discovered later.
The 1904 corpus scores **20.0%** and is reported at full size rather than folded away. It is 130 date cases against an engine with one date epoch — a known unimplemented feature showing up as exactly what it is, which is the correct behaviour for a measurement.
Two implementation notes that outlived the fix. Reproducing the positional cancellation rule required an **`Ast::Paren` node**: `=(0.1+0.2-0.3)` and `=0.1+0.2-0.3` must be able to differ, and an AST that folds parentheses away cannot express that. That node then had to be *rendered* in `usk-calc`'s R1C1 key rather than elided, because the key is the grouping key and grouping those two formulas together would give one of them the other's answer. And `ROUND` moved into the decimal domain: `floor(x * 10^d + 0.5) / 10^d` is the obvious implementation, and the multiply destroys the very digit being asked about — `2.675 * 100` is `267.49999999999997`.

**D-080 — TD-25 paid: the length prefix goes *outside* the canonical encoding, and unknown ops become `Payload::Opaque`.**
The question TD-25 left open was where the frame belongs. docs/26 answers it: the container's `payload` column must hold "the identical bytes that were hashed", so the canonical encoding of an op stays unframed and framing is a property of a *stream*. `Op::encode_framed` is `u32 big-endian length ‖ canonical bytes` — which is precisely what `ehkatra-relay`'s `put_ops` had been writing since Row 10. The wire had the framing all along; the snapshot body and the recovery tail did not, and that asymmetry was the debt. They now share one function.
Because the prefix is outside the hash, **no canonical op encoding moved**. The replay hashes did change (`ef7933e8…`/`5dbb01c2…` → `c79fa533…`/`b58d5505…`, native == wasm32) for the separate reason that docs/29 requires every payload variant to be in the replay-check generator, and `Opaque` is one — session 9's lesson was that a variant missing from that generator is a variant the determinism gate silently stops covering.
`Payload::Opaque(OpaqueOp)` holds the tag and the body privately, and `OpaqueOp::new` returns `None` for a tag this build knows. That makes "an opaque op smuggling a second spelling of an op we could have encoded ourselves" unrepresentable rather than merely discouraged — the D-060 technique again. `is_known_tag` and the decoder's match are two lists that must agree, so `every_known_tag_decodes_and_every_other_is_opaque` pins them to each other across all 256 tags.
Three semantic choices, each the conservative one:
* **An opaque op applies to nothing.** A build that cannot read an op must not guess what it meant. Consequence stated plainly: the *state* hash of a workbook legitimately differs between a build that knows a tag and one that does not. DP-A5 promises preservation, ordering and hashing — not cross-version state convergence, which is not achievable and would be a lie to claim.
* **It is accepted at the sync boundary, not quarantined.** Version skew is not hostility; refusing it would make every rolling upgrade look like an attack. It is still bounded (`MAX_OPAQUE_BYTES`), because DP-A5 obliges us to *store and retransmit* an op we cannot read, and that obligation is an allocation an untrusted peer controls.
* **It dirties nothing in the calc graph.** It changed no state, so treating it as structural would make an unreadable op force a full regroup on every arrival.
The test that states the point is `an_unknown_op_does_not_stop_the_ops_behind_it`: before framing, one op from a newer peer truncated every op behind it in a snapshot or a recovery tail. That is the failure mode, and it was silent.

**D-079 — TD-30 closed by architect ruling: three snapshots, and the op floor is the *oldest* of them.**
The ruling docs/16 now carries: *keep the last 3 snapshots plus ALL ops since the oldest retained snapshot; compaction may never leave the container in a state where a single corrupt snapshot loses acknowledged ops.* Both halves of D-075's candidate list were taken, because either alone still has a hole.
Two implementation guards follow from the invariant rather than from taste, and both are in `Container::compact`:
* **The floor is the oldest retained snapshot that *verifies*.** A snapshot authorising the deletion of ops it cannot prove it contains is exactly how one corruption becomes total loss. Verification is a full replay of the body, which is the expensive option and the correct one — this is the single moment where the container decides to destroy user data, and a checksum would only prove the bytes survived, not that they still mean what they meant.
* **Fewer than two verified snapshots prunes nothing.** Pruning to the oldest retained snapshot is only safe once a *fallback* exists; with one snapshot the tail is empty by construction, which is precisely the W-OPEN-1M failure. This makes the first compaction of every container a no-op for ops, and `a_first_compaction_prunes_no_ops_and_survives_losing_its_only_snapshot` is the regression test for the original defect.
With two or more nested snapshots the guarantee is structural, not statistical: whichever single snapshot is corrupt, the newest survivor covers at least the floor and the retained tail covers everything after it. Proven both ways — `corrupting_every_snapshot_but_the_oldest_still_recovers_every_op` (full recovery, `lost_data` false, and the user still told) and `corrupting_all_snapshots_rebuilds_from_the_full_op_tail` (ops are the truth).
Cost stated rather than hidden: while a snapshot body is the compacted op set, three snapshots hold three copies of the covered history. Filed as **TD-31**; it disappears when the body becomes docs/16's Merkle-shared tile image, where extra snapshots are O(dirty) — the same change TD-24's residual and TD-29 both wait on.
The honest boundary is tested too: after pruning, losing *all three* snapshots does lose what the floor absorbed, and `total_snapshot_loss_after_pruning_is_reported_rather_than_hidden` asserts the report says so. docs/16 forbids silent partial restore; it does not promise omnipotence.

**D-076 — TD-24's residual does NOT close at Row 11, contrary to the plan.**
The handoff expected a snapshot to give the state fold a checkpoint and make `settle()` cheap. It does not, and the reason is D-069: a v0.1 snapshot *body is the compacted op set*, and `Snapshot::verify` proves it by replaying it. Opening therefore costs replay(snapshot ops) + replay(tail), which is the same work as replay(whole log) — W-OPEN-1M's 2.10 s cold open is that replay, measured.
A snapshot becomes a fold checkpoint only when its body is a **materialised state image** (docs/16's Merkle-shared tile image), because only then can state be adopted without replaying. That is a genuine piece of work, not a wiring task, and pretending otherwise would have put a false "TD-24 closed" in the register. TD-24's residual keeps its trigger and moves to the tile-image body.

**D-071 — State is folded when it is read, not when the log grows (TD-24 largely paid).**
The obvious reading of TD-24 was "make `State` incrementally appliable", and that route is genuinely hard: a summary tile keeps no per-cell stamps to compare against, promotion must be decided before the first write lands, and the only known fix — a resident per-tile per-actor writer index — costs 2 KiB per (tile, actor) and would be catastrophic on a sparse workbook (W-SPARSE-SCATTER has ~58,000 tiles).
The cheaper observation is that the problem was never the fold, it was the *frequency*. DP-A9 already says caches are watermarked folds; `Session` was eagerly re-folding on every append instead. Appends now only record the batch, and `settle()` takes the fold on read — which is why `state()`, `value()` and `engine()` take `&mut self`. That signature is the point, not a nuisance: the type system now says "reading may cost you a fold", and a caller cannot observe stale state.
Measured on W-SYNC-RELAY, 50 replicas: **120 min → 6.8 min (17.6×)**, with dropped frames, reconnects, convergence time, the mid-run kill and every state hash **bit-identical** — which is the evidence that the change is a scheduling change and not a semantic one. Under sync, reads are ~50× rarer than appends (600 local edits versus ~30,000 delivered batches per replica), and that ratio is the speed-up.
*Residual debt, honestly:* a read after N appends is still O(N). Sync is append-heavy, so it wins; a UI repainting once per op would not. Row 11's snapshot is the named fix, unchanged.

**D-072 — The benchmark harness was measuring itself.**
Half of what looked like TD-24 was `Bus` calling `Replica::log()` — which clones every op — once per delivered frame, and once more per edit. At 30,000 ops that is a full deep clone of the log per message, so the instrumentation outgrew the system under test. Replaced with a borrow and a per-replica seen-set. Recorded because it changes how a number should be read: **the pre-fix wall-clock figures overstated the product's cost**, and a benchmark that allocates per observation is measuring the observer.
It also corrected a *measurement*, not just a speed: propagation was counted by scanning the receiving replica's log, so an op held in the causal-gap buffer (arrived, not yet applied) was counted again on redelivery, with a later timestamp. First-delivery is the honest definition of "propagated". p50 1,600 → 800 bus-ms and p95 5,800 → 3,700 at 50 replicas are that correction, not a performance win.

**D-069 — A v0.1 snapshot is the compacted op set plus the state hash it must produce, and loading it is a replay.**
docs/16 wants a content-addressed body "structurally shared via tile Merkle identity". That body is a Row-12+ format; inventing it now would put an unproven encoding under Row 11's recovery logic. So a v0.1 snapshot body is the compacted op set in the *same* canonical encoding the wire and the container already use — docs/26's "the file IS the wire format at rest", taken literally — and the tile image swaps in behind `Snapshot::verify` when it exists.
The consequential half is **how it is verified**. A checksum over the body proves the bytes survived; replaying them and comparing `State::state_hash()` proves the bytes still *mean* what they meant. DP-A2 makes the stronger check free, and it is what turns docs/26's migration rule ("a migration that changes the state hash is by definition wrong") from a sentence into an executable test. `verify` returns a `VerifiedSnapshot` that has no other constructor, which is how docs/27 §2's forbidden "opening READY without hash-verifying the loaded snapshot" becomes unrepresentable rather than a check someone could forget.
Rejected: a CRC/BLAKE3 body checksum alone (cheaper, and would have passed a snapshot whose ops decode to a different workbook after a codec change); and storing a serialized `State` image (faster to load, but it would need its own format, its own migration story, and would not verify against anything the rest of the system already computes).

**D-070 — Ops arriving during COMPACTING are deferred, not refused.**
docs/27 §2 forbids writing to the old file during COMPACTING *and* forbids any transition that loses acked ops. Satisfying either alone is trivial and satisfying both is the actual requirement, so the machine counts such ops into `acked_ops` (the RPO contract holds) while holding them out of the container (the compaction contract holds), and emits `FlushDeferred` after the atomic rename. Rejected: refusing the ops during compaction, which trades a durability violation for an availability one — the editor would have to block, and docs/16's "no Save, no dirty bit" means there is no moment at which blocking is acceptable.

### Session 9 (2026-08-07) — TD-09 closed

**D-061 — Promotion is per contested cell; the tile is only where stamps live.**
TD-09's three candidates were sub-tile blocks, compact per-cell stamps, and two-level summaries. Chose per-cell: a block size B only changes the amplification *constant* (promoted ≈ 1−(1−p)^B), whereas per-cell removes amplification entirely. `Meta::Promoted(tile)` became `Meta::Mixed { frontier, stamps }`, and the pre-pass now returns a per-tile *bitmap* of contested indices instead of a boolean, so an uncontested cell inside a mixed tile stays on the summary path.
Measured under W-TILE-10M: amplification **16,384× → 1×**; collab-pattern promotion 1.000% (== the contested rate); collab memory 11.09 B/cell / 123.6 MB, restoring A-001 under collaboration where it previously extrapolated to ~745 MB.
Fixed along the way: the tile's causal frontier was not advancing on contested writes, which would have made a tile look stale to anti-entropy (docs/15). Caught by the frontier assertion in `contested_cell_is_promoted_alone`.

**D-062 — A-002's pass bar is unachievable as written; not self-amended.**
docs/38 sets *<1% promotion at the collab pattern*, and the collab pattern contests 1% of cells by definition. A contested cell must carry metadata to name a winner and retain a loser (ADR-006), so promoted ≥ contested = 1% for **any** correct implementation. The measurement is exactly 1.000% — the floor, not a near-miss.
The intent behind A-002 (promotion must not amplify) is met and measured. The bar should be restated in amplification terms. **Deliberately not changed here:** docs/38 is normative, and loosening a bar one has just measured oneself against is the owner's call, not the implementer's. Filed per docs/00's "conflicting documents are defects" rule and surfaced in the session report.

**D-062 — CLOSED (owner ruling, 2026-08-08).** The owner restated the bar in docs/38 §W-TILE-10M in amplification terms: *promoted cells ÷ contested cells ≤ 1.5*, **and** collab-pattern RSS ≤ 400 MB, with no RSS bar at the adversarial pattern. The measured implementation is 1.0× amplification (the correctness floor) and 123.6 MB collab RSS, so it **passes on both halves**. docs/42 records A-002 as **Confirmed**. Nothing in the code changed as a result: the ruling restated the *bar*, not the *requirement*, and the requirement was already met. The escalation itself is the precedent worth keeping — an implementer who cannot meet a normative bar surfaces the conflict rather than editing the bar (DP-F5, docs/00).

### Session 9 (2026-08-07) — Row 9 exit criteria; new-spec deltas

**D-058 — The calc engine addresses cells by identity; `Rect` survives as derived index geometry only.**
TD-21 is closed: `Sheet`, `Cell` and `CellRef` are deleted, and `Engine` works over `State`. Formulas come from `State`'s registry; each reference is **rebound** from its stored identity bindings on every rebuild, so a structural edit needs no formula rewriting — the same bindings simply resolve to different positions (DP-A6 made executable).
`Rect` is kept, deliberately, and documented as *derived view coordinates*: a spatial index needs a total order on two axes, which identities alone do not provide. It is rebuilt from the axis order on every regroup and never outlives one, so a stale position cannot survive an edit. Deleting it entirely would mean inventing an identity-space index — that is TD-20's R-tree, not this row's work.
Measured cost recorded as TD-23: full recalc 53.0 → 92.6 ms on W-CHAIN-100K, both budgets still passing.

**D-059 — `Engine::observe(state, ops)` is the regrouping trigger (TD-18 closed).**
Structural and formula ops invalidate the graph (positions move, patterns change); value ops do not. `observe` inspects the batch and routes to `regroup + recalc_all` or `recalc_after`, so no caller has to remember which kind of edit it just made. `Session` feeds it every batch it applies, including remote ops arriving via `integrate`.

### Session 8 (2026-08-07) — Row 9 core: reducer, commands, selective undo

**D-055 — `SetFormula` ops carry identity bindings, bound once at the author.**
The op stores the source text (CST recoverable, ADR-011) plus one `RangeBinding` — four endpoint identities + anchor bits — per reference, in AST traversal order. Re-binding `A1` text on each replica against its own view would diverge under concurrent structural edits; carrying identities is DP-A7 applied to references. Tags 0x16–0x18 are new; 0x10–0x15 byte-identical, proven by the unchanged replay hashes.

**D-056 — Formula-vs-value LWW rides on canonical replay order; stamps deferred (TD-22).**
`State` keeps formulas in a flat identity-keyed map (docs/14 has formulas *reference* the group table, never packed among values). Whichever of `SetCell`/`ClearCell`/`SetFormula` applies last in canonical total order wins the cell — correct because both `State` constructors replay in that order. An incremental merge path (Row 10 sync) must carry per-entry stamps instead; recorded as TD-22 so sync cannot inherit this silently. The state hash gains a formulas section only when formulas exist, so every pre-Row-9 corpus hashes unchanged.

**D-057 — Undo semantics as implemented, including the two judgment calls.**
(i) *"Own write still wins" means the actor's write, not one op id.* First implementation compared the group's recorded op id and wrongly blocked undoing older groups after a newer undo had restored through a fresh op id. With LIFO undo order, an actor-scoped check is exactly docs/11's rule; only a foreign winner blocks.
(ii) *Prior-empty restores as a clear.* Ops cannot un-write history (DP-A1), so undoing the first write to a cell yields `Blank`, whose visible projection equals never-written. Recorded because "the projection is identity" is the undo law actually provable in an op-based store.
(iii) Undo of a delete emits `UndeleteRow`/`UndeleteCol` — the row returns *with its cells*, since deletion only ever tombstoned the identity. Redo is undo-of-undo through the same synthesis, so the directions cannot drift.

### Session 7 (2026-08-07) — Row 8, identity references

**D-051 — A reference is a pair of endpoint identities, resolved against the axis order that *retains tombstones*.**
docs/11 lists five behaviours — insert above leaves the span, insert inside extends it, delete inside shrinks it, endpoint deletion re-anchors inward, empty interval is `#REF!` — and says they "fall out structurally". They do, from one rule: an interval resolves to whatever is currently live *between* its endpoints. Nothing rewrites a reference on an edit, because a reference never named a position.
The one thing that rule cannot do without help is re-anchor inward, because "inward" is only meaningful against the order a deleted endpoint still occupies. `State` therefore exposes `full_row_order`/`full_col_order` — the axis order *including tombstones*, each tagged live. An earlier attempt carried the endpoints' bind-time ordinals as a hint instead; that is wrong, because ordinals shift under later edits and the hint silently decays into a lie. The tombstoned order is the only thing that stays true.

**D-052 — Property coverage is a seeded LCG sweep, not `proptest`.**
CLAUDE.md's stack list names proptest, and BOOTSTRAP row 8 asks for "a dedicated regression + proptest". The tests here instead use a hand-rolled seeded LCG, matching the convention already established in `usk-state` (`randomized_interleavings_converge`, explicitly "no rand dep").
Reason: DP-A2 wants a failure reproducible by seed alone, the workspace has one dependency and a complexity budget that exists to be defended (DP-S2), and the `supply-chain` CI gate has still never executed (session 3), so adding ~20 transitive dev-dependencies would be adding unverifiable surface. The *property* coverage BOOTSTRAP asks for is delivered — 200 randomized insert/delete sequences asserting resolution is always a contiguous live run, plus 60 shuffled arrival orders asserting resolution is order-independent.
This is a deviation from a recorded stack decision, so it is recorded rather than assumed. Revisit when the supply-chain gate has actually run green and shrinking would genuinely pay — proptest's real value is the counterexample minimiser, and these properties fail with small inputs anyway.
